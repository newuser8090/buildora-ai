# Phase P22-J — Data Integrations (Architecture)

> Scope (approved decisions D-J1..D-J6): a **minimal** data layer — durable
> collection definitions on the Project document, a pure binding resolver,
> static-snapshot export, collection CRUD + a Data/Binding inspector section,
> and a minimal "Add Supabase" guided flow with mock/Supabase provider parity.
> Explicitly OUT: form→collection writes, runtime-fetch exported sites,
> secrets in browser code, payments/email/analytics, and any broad integration
> suite. **P22-A through P22-I remain CLOSED** — every P22-J change below is an
> additive extension of an existing mechanism, never a redesign.

---

## 1. Model (D-J1, D-J2, D-J3)

- **`Project.collections?: Collection[]`** — durable, document-level, optional
  (old projects load unchanged, no migration bump). `Collection` is exactly:
  `{ id, name, fields }` where `fields: { id, name, type }` and
  `type: "text" | "number" | "boolean" | "image" | "url"`. No records array
  in the document — runtime records belong to the integration/provider layer.
- **Deterministic ids** — `col-<slug>-<seq>` for collections, `fld-<seq>` for
  fields, generated by pure helpers in `collection-structure.ts`.
- **Canonical validation boundary** — `CollectionsSchema` +
  `CollectionFieldSchema` (Zod, bounded: max collections/fields/name lengths,
  known types) in `schemas/collection-schema.ts`; `Project.collections`
  validated by the same `ProjectSchema` used everywhere
  (`generation-plan-schema.ts`).
- **Persistence** — `project-serializer.ts` and `project-normalizer.ts`
  allow-list extended with `collections` (P22-F optional-field precedent);
  `serialize → deserialize → normalize → validate` preserves collections and
  old projects without collections remain valid.
- **Collaboration** — the CRDT `tree-normalizer.ts` carries `binding` through
  the existing `carryValidatedElementField` mechanism and projects
  `collections` through the collab payload; the stored custom-block node
  schema (`custom-block-schema.ts`) gains optional `binding`
  (re-validated with the shared `ElementBindingSchema`).

## 2. Binding resolver (D-J4, D-J6)

- **Pure shared resolver** — `src/features/elements/binding/resolve.ts`,
  patterned after `asset-resolver.ts`: pure, deterministic, never throws,
  no React/DOM, no eval / Function constructor / arbitrary property access.
- **Path grammar** — bounded + allow-listed: identifiers with optional
  numeric array subscripts (`price`, `product.name`, `images[0].src`), max
  depth 4, max length 512, single token type. Explicitly rejected: `..`,
  `__proto__`, `prototype`, `constructor`, absolute paths, quotes/spaces,
  unbounded syntax.
- **Resolution contract** — `resolveBinding(binding, context)` returns a
  structured `resolved | unresolved(reason)` result. Only `source:
  "collection"` is resolved; `page/project/form/auth` remain future
  capability and resolve as `unsupported-source` (never dead unsafe
  behavior). Missing collection/field/record/path and unsafe values all
  return structured unresolved results.
- **Type coercion** — only string/number/boolean; `image` values pass the
  image-URL policy, `url` values pass the link-URL policy (self-contained,
  mirrors the BlockRenderer/export policy). All collection values are inert
  data — never raw HTML or executable code.
- **Prop-level helpers** — `resolveNodeBindingProps` (render + export share
  it) merges the resolved value into the node's props only for the bound
  field; unresolved bindings leave the static prop untouched (identical
  unbound behavior).

## 3. Rendering and export

- **Renderer** — the existing `BlockRenderer.tsx` (P22-G path) is the only
  rendering path. `BlockNodeRenderer` resolves `node.binding` through
  `resolveNodeBindingProps` (memoized on node/collections/records) and reads
  the resolved props (text, href, src, …). Unbound nodes and unresolved
  bindings render exactly as before. The canvas preview (`CustomBlockSection`)
  passes `project.collections` + integration `records` into the renderer.
- **Export — STATIC SNAPSHOT (D-J4)** — `export-pipeline.ts` first validates
  the original project (dangling collection references rejected by the
  `export-validator.ts`), then bakes every binding: resolved values are
  written into node props and binding metadata is removed (`bakeTreeBindings`
  in `resolve.ts`). No Supabase calls, no runtime fetch, no secrets, no
  dynamic code — the baked payload is plain inert JSON-safe data.
- **Validator** — `export-validator.ts` rejects dangling collection
  references (binding whose collectionId no longer exists) and `custom-block`
  is added to the fallback known-type list so tests without the live registry
  validate like production.

## 4. UI

- **Data tab** — new `RightSidebar` tab ("Data", `right-tab-data`) hosting
  `DataPanel`: integration status + minimal "Add Supabase" guided flow
  (D-J5) + collection management (create / rename / delete collections,
  add / remove / rename / re-type fields). Every action routes through the
  editor store's `withHistory` boundary — one atomic undo entry each.
- **Inspector Data section** — new `source: "binding"` field kind in the
  existing `elements/inspector` architecture (types → mutate → resolver →
  fields → schemas) plus the `BindingField` control in
  `inspector/components/controls/BindingField.tsx`: shows bound state,
  source, collection, element field, path, and broken/unresolved state; every
  discrete interaction commits ONE complete validated `ElementBinding`
  through `commitField` → `commitElementTree` → `withHistory`. The existing
  `ElementBindingSchema` / `updateElementBinding` are reused — no second
  binding system.
- **Records refresh** — `DataPanel` refreshes provider records whenever the
  durable collection set changes, so bound elements resolve immediately in
  the preview.

## 5. Integrations (D-J5)

- **Provider abstraction** — `src/features/integrations/*`:
  `types.ts` (contract), `environment.ts` (mirrors cloud-sync conventions:
  Supabase env → supabase; `NEXT_PUBLIC_DATA_PROVIDER=mock` or development →
  mock; else none), `mock/mock-data-provider.ts` (deterministic demo records
  derived from field definitions, re-derived when field definitions change;
  in-memory only), `supabase/supabase-data-provider.ts` (calls the
  SECURITY DEFINER RPCs with `auth.uid()` + workspace membership checks),
  `provider-factory.ts` (singleton resolution), and
  `store/data-integration-store.ts` (runtime-only records; durable state stays
  in the editor store).
- **Secrets stay server-side** — browser code sees only
  `NEXT_PUBLIC_SUPABASE_URL` + `NEXT_PUBLIC_SUPABASE_ANON_KEY`; the
  service-role key never appears client-side.
- **Additive migration** — `supabase/migrations/20260814000001_data_records.sql`
  only: a `data_records` table + SECURITY DEFINER list/upsert/delete RPCs
  gated by `auth.uid()` + existing workspace-membership authz. No existing
  migration/RLS touched, no authz weakened.

## 6. Test plan coverage

Collections schema (valid/invalid/bounds/optional/old-project compat),
resolver (direct/nested/array/missing/safety/coercion/determinism/never
throws), persistence round-trip + old-project compat, collaboration
binding carry + drop-invalid, store CRUD + undo/redo single-entry, rendering
bound/unbound/unresolved, export bake + dangling-reference rejection +
inert-data (no code execution), security (traversal/pollution/injection/
leaks/unsafe URLs), provider parity (mock ≡ Supabase contract), and ONE
mock-parity E2E covering connect → create collection → bind → preview
resolves → export bakes → reload persists.

## 7. Explicit non-goals (scope guards)

No P22-K/P23, no runtime-fetch exported websites, no form writes, no custom
code execution, no new AI providers, no new dependencies, no payments/email/
analytics, no broad integration suite, no reopening of P22-A..I.
